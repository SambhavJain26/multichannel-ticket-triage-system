## Planning Decisions Already Made

- Build is demo-depth, not production.
- Architecture is email/form/fixture in, local n8n orchestration, local Postgres storage, OpenAI strict JSON calls, Telegram manager alerts via tunnel when callback testing is needed, SMTP approved replies, and server-rendered board.
- No PMS integration in the demo.
- Advisory-only is non-negotiable: no dispatch, no suppress, no auto-close, no auto-reply without human approval.
- Age-based routine escalation becomes `OVERDUE` board/digest status only. It does not create an emergency phone alert.
- Deterministic safety rules are escalate-only and run after the model.
- `NEEDS_REVIEW` is a system state, not a model output.
- Accommodation/legal-sensitive requests skip draft generation and require human handling.
- Competitor-aware positioning is required; do not claim nobody else does maintenance AI triage.
- Default setup is local-first. VPS and Caddy are reserved for production deployment.
- Use a tunnel for Telegram callback testing and temporary public board access.
- Use HTTP Request for workflow model calls in this local n8n build. The installed n8n `2.29.10` OpenAI node is the older hidden node and does not expose Responses API, strict JSON Schema, or reasoning settings. Direct API calls remain useful for the standalone harness.
- Do not use n8n AI Agent/LangChain agent loops for the triage classifier.
- The current live workflow model is `gpt-5.6-luna`, selected after direct-demo classification instability with `gpt-5-nano`. Historical Stage 3 scorecards remain nano measurements. Use standard pricing for live workflow estimates; batch pricing is only relevant for offline batch harness/report runs.
- Early approved outbound replies should go to controlled test inboxes until the approval gate and double-approve guard are verified.
- Stage 7 real-mailbox path uses one Gmail/Workspace mailbox with two n8n credentials: `maintenance-triage-demo-imap-domain` and `maintenance-triage-demo-smtp-domain`. The app password must be entered locally, not committed or pasted into chat.
- Stage 9 uses a separate tenant Telegram bot while retaining the existing manager Telegram bot. Airtable is the manager-facing workspace and vendor/tenant roster source; Postgres remains the durable source for ticket, conversation, and one-send-only state. Email/form intake sends only a `[MT-SYSTEM]` Telegram onboarding email. The IMAP path ignores this prefix so a shared Gmail test mailbox cannot loop its own system messages back into triage.

- Stage 5 webhook correction: imported n8n Webhook nodes without a fixed top-level `webhookId` register under a generated workflow/node-prefixed path in local n8n `2.29.10`. The board workflow pins `webhookId: board` and restarts n8n after import so `/webhook/board` is registered.
- Stage 5 response-code correction: local n8n `2.29.10` did not reliably apply a nested `options.responseCode` expression in Respond to Webhook. The board workflow routes not-found and normal responses to separate Respond nodes with literal 404 and 200 codes.
- Stage 5 detail-view correction: raw model/event JSON is useful for auditability but too technical for the normal manager view. Detail pages now show a plain-language AI readout and event descriptions first, with raw JSON kept behind collapsed technical audit disclosures.
- Stage 6 import correction: generated n8n workflow IDs must stay within the local database `varchar(36)` limit. Stage 6 uses short internal IDs with descriptive workflow names.
- Stage 6 routing correction: n8n strict IF nodes require actual boolean values; Code nodes now coerce guard fields such as `should_send_email` explicitly.
- Stage 6 live-callback correction: Telegram Trigger workflows are imported but not published by default because activation needs a current HTTPS tunnel and real chat IDs. Use `scripts/check-stage-6-live-prereqs.ps1` first, then `scripts/import-stage-6-workflows.ps1 -PublishTelegramCallback`.
- Stage 6 live Telegram correction: Telegram Trigger node names must avoid spaces in this local n8n version, or the registered webhook path can diverge from Telegram's configured path. The callback trigger is named `TelegramCallbackTrigger`.
- Stage 6 live alert correction: Telegram inline keyboards must be explicit fixed-collection rows in the Telegram node; passing the whole keyboard as an expression produced plain text alerts with no buttons. Real alerts now route through emergency, urgent, and review-specific Telegram send nodes.
- Stage 6 callback correction: Telegram `answerQuery` does not preserve the approval-action JSON for downstream nodes. The callback workflow reattaches the approval context before editing the Telegram message.
- Stage 6 status correction: alert recording must not regress already handled tickets back to `ALERTED`. Handled tickets are skipped, and successful alerts clear stale `last_alert_error`.
- Stage 7 connector correction: the Stage 4 core workflow can write tickets successfully while returning no downstream items through Execute Sub-workflow because its result branches are routed. Stage 7 connectors now treat the core as a database-writing side effect, then reselect tickets by `msg_id` for roster matching and alert dispatch.
- Stage 7 live trigger correction: publishing the real Gmail IMAP trigger against an inbox with existing unread mail immediately ingests those messages. Use a dedicated mailbox, or clear/archive unrelated unread mail before publishing live triggers.
- Stage 7 live alert correction: Telegram inline button URLs must be public HTTPS URLs. Set `triage.config.board.public_base_url` to the current tunnel URL before running real Telegram alert tests; otherwise the alert can fail with a localhost board URL.
- Stage 7 Form Trigger correction: local n8n `2.29.10` registers the imported form under a workflow/node-prefixed form path. The current local form URL is `http://localhost:5678/form/mt-form-ingest-stage-7/tenantreportform/report-issue`, not `/form/report-issue`.
- Stage 7 fixture-safety correction found during Stage 8: `test_mode` was lost across the Postgres roster match node, causing fixture rehearsal emergencies to send real Telegram alerts. The Stage 7 post-ingest workflow now carries `test_mode` through SQL output before alert dispatch.
- Stage 8 model-stability correction: repeated n8n/OpenAI rehearsal exposed occasional `gpt-5-nano` variance on the live-demo fixtures. The Stage 4 rule layer now keeps squeaky/noisy door-only complaints `ROUTINE`, keeps contained ceiling drips with a bucket `URGENT` unless spreading/collapse/electrical hazards are present, and avoids forcing high-confidence basic-service Spanish messages to `NEEDS_REVIEW` solely because the model reports `trade: UNKNOWN`.
